# 折叠与真实上下文的实测

界面右侧一次对话里画了三个「系统提示词」行，而模型真正读到的上下文里
`system/message` 只该有一条。这份文档先把判据定死，再起一个全新会话去实测，
最后逐条对账：对不上，就是实现或界面投影出了问题。

## 1. 判据

| # | 判据 | 期望 | 依据 |
|---|---|---|---|
| 1 | 表层里 `system/message` 的条数 | **恰好 1 条** | 折叠只会 `replace` 掉一段用户侧内容，不会新增系统消息；界面上多出来的那几行不是上下文里的东西 |
| 2 | 折叠通告的正文 | `tree_task消息：隐藏了N条过程上下文。`，有文件读写时后面另起 `读取：…` / `写入：…` | `region.js` 的 `renderSummary` |
| 3 | 折叠区间 | 从「上次 `tree_task_done` 之后的第一个 `create` / `plan`」之后，到本次 `done` 之前；中间的 `create` / `plan` **不是**切点 | `region.js` 的 `foldRange`、`docs/06-折叠范围规则.md` |
| 4 | 起止两次调用的调用与返回 | 起点那次调用与本次 `done` 的调用与返回全部留在表层上；**被跨过的**其它 `create` / `plan` 随过程一起收走 | 同上 |
| 5 | 区间里夹着真人消息 | **整段不折**，表层里找不到那一次折叠 | `region.js` 的 `foldOnce` |
| 6 | 区间为空（起点那次调用与 `done` 紧挨着） | **什么都不注入** | `foldRange` 返回 null |
| 7 | 每一次 `tree_task_done` 的调用与返回 | 都还在表层上，一轮轮累积 | `foldOnce` 的区间止于 done 之前 |
| 8 | 折叠次数与 `reason=series` 的请求 | 每发生一次 `replace`，紧接的请求 `reason` 就是 `series`，次数应一一对应 | DSH 的 `replaceGeneration` 语义 |

判据 1 与 8 是回答"界面和真实上下文差在哪"的关键：界面在 `reason != change`
的请求上都会画一张系统提示词卡片，而上下文里的系统消息自始至终只有一条。

## 2. 步骤

```powershell
cd C:\apps\dsh_workspace\exp\_harness

# 1) 起一个全新的 headless 会话（新进程，跑的是 host 当前加载的插件代码）
dsh --profile headless (Get-Content .\fold-test-prompt.txt -Raw)

# 2) 找到刚产生的会话日志
$x = Get-ChildItem "$env:USERPROFILE\.dsh\sessions" -Recurse -Filter session.v3.jsonl.zstd |
     Sort-Object LastWriteTime -Descending | Select-Object -First 1
$x.FullName

# 3) 重建表层（模型真正看到的那串消息）
node surface-report.mjs $x.FullName --out 表层-折叠实测.md

# 4) 看每次请求的 reason，与折叠次数对账
node request-report.mjs $x.FullName
```

`surface-report.mjs` 按 `surfaceOp` 重放日志：`append` 追加到尾部，`replace`
原位换掉一段——重放出来的那一串就是模型实际读到的上下文，和会话日志（append-only，
被替换掉的内容还在里面）不是一回事。

## 4. 结论

**上下文本身没问题，差在界面的投影。**

- 模型读到的系统提示词自始至终只有 **1 条**；折叠没有新增任何系统消息，它只把两段过程换成了两条计数通告。
- 界面上的**每一张「系统提示词」卡片对应一次 `reason=series` 的请求**，而 `series` 正好等于折叠次数
  （本次 3 次）。因果链是：折叠 → `replace` → `replaceGeneration` 递增 → 下一次请求带 `reason=series`
  → 界面在 `reason != change` 的请求上重画系统提示词卡片。
- 卡片为什么不复用同一处：`dsh-client-ui-chat` 的 `stableRequestPromptAnchor`
  （`lib/client.js:6105`）只在"当前 chat 节点本身就是 system-prompt"时才沿用旧锚点；中间隔着工具行时
  会走 `requestPromptAnchor`（`:6098`）按当轮 step 的起点另算一个锚点，于是新起一张卡片。
  也就是说，**折叠几次，界面就多几张系统提示词卡片**，而上下文里一条都没多。

要让界面上不再堆这几张卡片，只能减少 `replace` 次数（比如把折叠攒到一轮里做一次），
插件本身没有别的办法——这不是它伪造出来的上下文。

## 5. 新起点规则下的复测

上面的实测数据取自**旧起点规则**（起点 = 表层里上一个边界调用）。起点改为
「上一次 `done` 之后的第一个 `create` / `plan`」之后，用同一条通路复测了一遍。

- 会话 `session-720a83e4`（headless 新进程，cwd = `exp/_harness`，模型 deepseek-flash），
  prompt 见 `exp/_harness/fold-v2-prompt.txt`，表层重建见 `exp/_harness/表层-折叠-v2.md`。
- 序列：`tree_task_create`(#15 调用 / #17 返回) → 过程（`read`、`tree_task_plan`、`pwsh`
  三组调用与返回，共 6 条 #20..#32）→ `tree_task_done`(#35 调用 / #37 返回)。
- 折叠 1 次：`seq=39` 收走 `#20..#32` 六条，正文
  `tree_task消息：隐藏了6条过程上下文。读取：C:\…\exp\_harness\fold-test-prompt.txt`。

**最关键的一处**：被跨过的 `tree_task_plan` 的调用与返回这一次**确实进了折叠**
（旧规则下它们会作为"上一个边界调用"留在表层，只有 `plan` 之后的 6 条过程被收走）。

表层最终 11 个节点：

一个侧面证据：`done` 之后模型又调了一次 `read` 去重读 `fold-test-prompt.txt`（#42/#44），
因为它在 `create` 之后读过的那次内容连同 `tree_task_plan`、`pwsh` 一起被这次折叠收走了。
这是新规则收缩得更彻底的直接后果——收走的内容更多，模型要重新取用就得再读一次。
