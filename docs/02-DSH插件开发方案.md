# dsh-task-tree 插件设计

把一件需要多步做完的事组织成**目标 → 任务 → 子任务**三级树，让每个节点完成时
由模型提交结果，插件随即把这个节点的**执行过程**从上下文里折叠掉。

---

## 1. 它解决什么

DSH 已有 goal、todo、plan mode 三套任务相关设施，但都不解决这两件事：

| 问题 | 现状 | 本插件 |
|---|---|---|
| 多步任务的**结构** | `todo_write` 是一张扁平清单，整表替换、无层级、无 id | 三级树，逐节点增删改 |
| 上下文**只增不减** | 历史越堆越长，压缩是全局兜底、被动触发 | 每个节点的过程占一段，做完就整段换掉 |

第二条是重点。它关心的不是"压得够不够狠"，而是**每一段上下文的归属
问题**：一段内容属于哪个节点、这个节点什么时候结束、结束了这段内容还有什么用。

长任务跑到后半程，上下文里绝大多数内容是过程：读过哪些文件、试过哪些错、执行过
哪些命令。这些对后面没有用，却一直占着位置——每多一轮，要喂给模型的就越长。

真正需要留给后面的只有一句话：**这一步做完了，它产出了什么。**

| | 内容 | 去向 |
|---|---|---|
| 过程 | 读文件、试错、命令输出 | 节点完成时整段折叠掉 |
| 结果 | 模型在 `tree_task_done` 里提交的 `result` | 留下来，供后续节点引用 |

和压缩的区别在这里：压缩是被动的、按量的，触发了才丢；折叠是主动的、按结构的，
**节点一完成就精确地把它那段收走**，不多丢也不少丢。

## 2. 上下文组成

```
[节点 0]  系统提示词（身份 / 工具 schema / 静态说明）   ← 会话内逐字节不变
[用户消息]
[目标级汇总]                          ← 换目标时逐条累积
  [任务级汇总]                        ← 换任务时逐条累积
    [子任务汇总] [子任务汇总] …       ← 同级逐条累积，互不卷走
    [当前子任务的执行过程]            ← 下一次折叠的对象
```

三部分各有明确职责：

| 部分 | 内容 | 变化频率 | 缓存 |
|---|---|---|---|
| 节点 0 | 身份、工具 schema、静态说明 | 永不变化 | 永远命中 |
| 汇总消息 | 已完成节点提交的结果 | 每完成一个节点追加一条 | 已落下的逐条命中 |
| 执行过程 | 当前活跃节点的全部来往 | 每次折叠被整段替换 | 只有这一段重算 |

**节点 0 必须逐字节不变。** 它一变，整个上下文从第一个 token 起失去缓存。
所以插件的系统提示词段落是**静态**的：只说明这组工具是什么、怎么配合用，
不放任何随计划变化的内容。计划的当前状态由 `tree_task_status` 现取。

---

## 3. 三级树

```
目标 (goal)
 ├─ 任务 (task)
 │   ├─ 子任务 (step)
 │   └─ 子任务 (step)
 └─ 任务 (task)
     └─ 子任务 (step)
```

层级**固定三级**，不增不减。子任务是最低一级，不能再往下拆。

节点状态只有三种：

| 状态 | 含义 |
|---|---|
| `pending` | 还没结束 |
| `done` | 已完成，`result` 里有它提交的结果 |
| `dropped` | 已丢弃（改需求用） |

`done` 和 `dropped` 合称**已结束**——两者都值得把执行过程收起来。

`activePath(plan)` 推导出当前活跃的三级节点：每一层取第一个 `pending` 的节点。
它同时是"当前该推进哪一层"的唯一依据。

## 4. 游标与折叠

### 4.1 游标

每层一个游标，记着"这一层总结到哪儿了"，形状是 `{ key, cursor }`：

- `key` —— 该层当前节点的 id。与上一轮不同就说明这一层换节点了。
- `cursor` —— 该层折叠的**边界节点 seq**。折叠时从它**之后**替换到末尾，
  它自己留在 surface 上。

`cursor` 有两个来源：新开一层时是**进入那一刻 surface 的末尾节点**；折叠一次之后
就变成**刚落下的那条汇总消息**。所以它指向的不一定是本插件放下的节点——第一次
折叠之前，它可能指向别的生产者留下的内容。判定游标是否可用只看**它还在不在
surface 上**，不要求它是本插件放的。

`cursor` 为 `null` 表示进入这一层时 surface 还是空的，没有可保留的边界。

### 4.2 折叠范围

```
子任务完成 → 替换 [上个子任务汇总之后, 末尾] → 本子任务的汇总
任务完成   → 替换 [进任务时的边界之后, 末尾] → 本任务的汇总
目标完成   → 替换 [进目标时的边界之后, 末尾] → 目标的汇总
```

**游标留在替换范围之外**，所以同级上一条汇总不会被这一次折叠卷走。
这就是"同级完成不互相屏蔽"的来由，也是结果能逐条累积的原因。

起点一律是 `cursorIdx + 1`（位置索引），不是 seq 加一。

### 4.3 一个节点还是多个

一个 key 和下一个 key 之间可能挤着好几个节点——模型在一轮里连着完成两个子任务，
或者中间那个被丢弃了。它们同属一段执行过程，收成**一条**汇总就够。

所以折叠时按树里的顺序往后数，取**连续已结束**的节点，遇到第一个还没结束的就停：
那正是这一层现在的活跃节点。

### 4.4 时机

折叠挂在 `agent/pre-step`，并且**必须 `await next()` 之后再动手**：
上一轮已结束、下一个请求还没构造，此时本步的一切决定都已落定。

工具执行中途不能折叠——那一刻 surface 还在增长，替换会把自己也卷进去。

顺序也不能颠倒：**先折叠、后对齐游标**。折叠要读换节点**之前**的游标，
而 `syncCursors` 一跑就把游标推到当前末尾，那时再也没有折叠的起点了。

### 4.5 降级为追加

游标一旦失效——被压缩遮掉了，或它之后本来就什么都没有——就没有可替换的区间。
这一次折叠**降级为纯追加**：执行过程收不起来，但提交的结果照样进上下文。

> **收不起来可以，丢掉结果不行。** 结果是这个节点唯一的出口，模型再也看不到
> 它产出了什么，整棵树就断了。

折叠失败（`session.append` 抛错）同理：记一条 warn，**不推走游标**。
推走了这段过程就再也折不掉。

### 4.6 汇总消息的形态

```
role:    user
content: [{ type: "text", text: <各节点提交的结果> }]
source:  { kind: "plugin", plugin: "dsh-task-tree", form: "notice", summary: <一行摘要> }
```

用 `notice` + `summary`，界面把它渲染成一行可读的说明，展开才是正文。

刻意**不用 `snapshot`**——那是"运行时上下文快照"的专属标签，借用它会让任务汇总
在界面上冒充系统提示词或运行环境快照。

用 `user/message` 而**不是伪造 `tool/result`**：后者必须紧跟一条同 `callId` 的
assistant `tool_call`，伪造会被协议校验拒绝。

正处在检查点上时，检查点提示一并附在汇总正文末尾——那一刻模型正需要知道
"这一层只剩拆子节点和提交结果两条路"，而这条消息就是它接下来唯一会读到的说明。

### 4.7 替换的固有代价

DSH 把"上下文被替换过"记成一次请求序列的边界（`replaceGeneration` 递增）。下一次
请求因此带上 `reason=series`，界面在 `reason` 不是 `change` 的请求上都会重新渲染
系统提示词卡片——**但提示词一个字都没变**。

界面复用的是同一个锚点，所以卡片不会变多、位置也不动，只是随每次折叠刷新一遍。
这是 DSH 的固有语义，插件绕不开，只能把替换次数压到最低：**从外往里走，碰到第一层
换了就停**。外层换了，内层的一切本来就在外层的替换范围里，再折一次只会把外层刚
落下的汇总又卷走。剩下的交给 `syncCursors` 重建。

## 5. 检查点

**子任务全部结束，不会让父节点自动完成。** 那一刻树进入**检查点**：

```
检查点：任务「重构解析器」(t-3) 的子节点已全部结束。
此刻只放行两个工具：tree_task_plan（继续给 t-3 拆子节点）与
tree_task_done（提交这个任务的结果并完成它）。
```

检查点期间**只放行 `tree_task_plan` 与 `tree_task_done`**，其余工具一律被拒。

为什么要这个状态：子节点做完，不等于"这一层做完了"。是继续拆还是就此收口，
是个需要判断的决定，**不能被计数规则替模型定死**。把它做成一个显式的、工具面被
收窄的检查点，模型就必须停下来面对这个问题。

检查点闸门挂在 `tools/pre-execute` 上，**只拦模型，拦不住人**：
`/task-tree` 命令随时能提交结果、丢弃节点、或者把自动续行停掉。

## 6. 工具集

全部以 `tree_task_` 开头，共六个。

| 工具 | 用途 |
|---|---|
| `tree_task_status` | 查看整棵树、各节点状态与已提交的结果，以及现在该推进哪个节点 |
| `tree_task_create` | 建立计划：一个目标 + 若干任务。会替换现有计划 |
| `tree_task_plan` | 给一个节点追加子节点：给目标追加任务，给任务追加子任务 |
| `tree_task_done` | 完成一个节点并提交它的结果，`result` 必填 |
| `tree_task_update` | 修改一个节点的标题或说明 |
| `tree_task_drop` | 丢弃一个节点；丢弃任务会连同它的子任务一起丢弃 |

`result` 缺失或全空白一律拒绝，且**不改节点状态**——半完成的节点比没完成更糟。
重复 `complete` 一个已结束的节点也会被拒，而不是静默改状态。

工具的 `parameters` 写的是**裸 JSON Schema**，不是宿主 SDK 的类型助手：
以 `link:` 方式安装的插件从自己的目录往上找不到宿主作用域的包，
import 任何 `@deepseek-ai/*` 运行时模块都会在加载时直接炸掉。

## 7. 系统提示词

**只有一个段落，静态，会话内逐字节不变**，注册名 `dsh-task-tree`，默认 order `2000`
（在部署人设 0、计划策略 500 之后，所有内置工具指引之前）。正文见 `lib/prompt.js`。

注册必须包在 `ctx.effect()` 里，否则热更新后会重复注册而抛错。

## 8. 自动续行

`autoContinue` 默认关闭，开着也只是**兜底**：`tree_task_done` 的返回文本里已经带了
"请继续执行下一个子任务"，模型通常会在同一轮里接着做。这里兜的是模型仍然停下来的情况。

四道闸门，缺一不可：

| # | 闸门 | 作用 |
|---|---|---|
| 1 | 默认关 | `autoContinue: false` 时不注册续行逻辑 |
| 2 | 中断即停 | 用户按下停止（`signal.aborted`）后这个会话不再被自动唤起，直到真人再发消息 |
| 3 | 内置 goal 优先 | `goals` 服务里有活跃 goal 就完全让路 |
| 4 | 轮次上限 | 连续续行达 `maxAutoRounds` 即停 |

队列里还有排队输入（`inbox.nextTurn` / `nextStep` 非空）时也不抢，让用户先说话。

**配额只由真人消息重置。** 必须按来源区分（`source.kind === 'user'`），
不能按"这一步有没有消息"：插件自己用 `agent.followup()` 推的消息同样会进入下一步的
`payload.messages`，那样每一轮都会把自己刚用掉的配额重置回去，`maxAutoRounds` 就失去意义。

**绝不挂在 `dsh-goal-round-driver` 上。** 它每推进一轮都设 `startsRequestSeries: true`，
会让系统提示词走归一化分支；一旦节点 0 被判定需要重写，整个上下文从第一个 token 起
失去缓存。

## 9. 开关与界面

### 9.1 默认不启用

`enabled` 默认 `false`。一启用，插件就会往**每个会话**的系统提示词里加一段说明、
并在节点完成时改上下文——这种事不该在用户没点头的时候发生。

未启用时注册路径刻意收窄：不注册工具、不加提示词段落、不挂 `agent/pre-step`、
不挂检查点闸门。只注册两条**只读**入口，让人能确认"装了但没开"以及怎么开：

- `/task-tree` 命令（返回未启用说明）
- 面板 HTTP 接口（设置页要能显示启用后的影响）

### 9.2 斜杠命令

`/task-tree` **不经过模型**，`handler` 直接执行、直接返回文本：

| 命令 | 作用 |
|---|---|
| `/task-tree` | 查看本会话的任务树与检查点状态 |
| `/task-tree done <id> <结果>` | 提交某个节点的结果并完成它 |
| `/task-tree drop <id>` | 丢弃某个节点 |
| `/task-tree stop` | 停止本会话的自动续行 |
| `/task-tree resume` | 重新允许自动续行 |
| `/task-tree reset` | 清掉本会话的计划树 |

### 9.3 任务树条目

注册到 `conversation.input.dock`——输入框上方的整宽条目区，和内置的待办、目标条目
并排。宽度按内置条目的算法算：

```
width:        calc(100% - 2×side-clearance - 4×dock-inset)   /* 100% - 64px */
max-width:    calc(composer-card-max-width - 4×dock-inset)
margin:       0 auto
```

`card-max-width` 等于 `chat-content-width + 32px`，而 `32px = 2 × side-clearance`，
所以 `max-width` 正好等于 `chat-content-width`——**与消息正文同宽**。
`chat-content-width` 从会话列宽动态算出，窗口缩放时会跟着正文一起变。

### 9.4 设置页

注册到 `settings.section`，显示插件当前是启用还是未启用，并逐条列明启用后会影响什么，
以及怎么开、怎么关。

## 10. 状态与持久化

全部在 `$DSH_HOME/dsh-task-tree/` 下，**以 `sessionId` 为键**：

| 文件 | 内容 |
|---|---|
| `plans/<sessionId>.json` | 计划树（每个会话一棵） |
| `surfaces/<sessionId>.json` | 三层的折叠游标 `{ key, cursor }` |

计划属于建立它的那个会话。放到会话无关的位置，任何一个会话的计划都会被所有会话的
`agent/pre-step` 读到——那等于把不相干的节点指派塞进别人的上下文，还会让别的会话
顺手改掉这棵树。

写入一律走「临时文件 + rename」：同一文件系统内 rename 是原子的，进程崩在写入中途
也不会留下半截 JSON。读到的坏文件按空状态处理，下一次写入会覆盖它。

## 11. 工程结构

```
dsh-task-tree/
├─ package.json          dsh.bundle.patch / dsh.client 声明
├─ cordis.patch.yml      bundle 层：把 task-tree 这一行插进 profile
├─ enable.example.yml    启用示例
├─ client.js             前端：任务树条目 + 设置段
├─ lib/
│  ├─ index.js           入口：配置兜底、启用/未启用两条装配路径
│  ├─ plan.js            计划树纯逻辑：状态流转、activePath、checkpointOf、渲染
│  ├─ store.js           状态读写：plans/ 与 surfaces/，原子写
│  ├─ region.js          折叠：游标同步、折叠范围、汇总消息
│  ├─ tools.js           六个工具 + 检查点闸门
│  ├─ prompt.js          静态系统提示词段落
│  ├─ commands.js        /task-tree 命令
│  ├─ http.js            面板与设置页的 HTTP 接口
│  └─ auto-continue.js   自动续行兜底
├─ verify-*.mjs          自检（不随包发布，见 files 白名单）
└─ docs/                 设计文档
```

### 11.1 必须遵守的契约

这些是硬约束，改动时必须保持：

1. **`ctx.tools` 必须写进 `inject`。** cordis 在访问一个没有 inject 的服务属性时
   直接抛 `cannot get property "tools" without inject`，整个插件加载失败、dsh 起不来。
   拿到其他可选服务用 `ctx.get()`（反射式路径不抛）。

2. **替换保持位置。** DSH 用 `nodes.splice(startIdx, count, seq)` **原位**换掉被遮蔽的
   节点，所以 replacement 节点**保留它原来的位置索引**，`surface.nodes` 因此
   **不是 seq 递增的**——系统提示词被重写过之后，它的 seq 可能比它后面的用户消息大得多。

3. **起止一律按位置索引取。** DSH 自己算 `nodes.slice(startIdx, endIdx + 1)` 也是位置
   区间。按 seq 区间筛选会在上面那种乱序下漏掉节点。

4. **`sourceEventSeqs` 必须覆盖全部被遮蔽的节点。** DSH 的 provenance 校验要求
   每一个被遮蔽节点的 seq 都在里面（多列无妨，少列一个直接拒绝）。

5. **节点 0 的重写约束。** 若替换区间从索引 0 开始、且节点 0 是 `system/message`，
   替换结果必须**自己也是一条 `system/message`，且恰好覆盖那一个节点**。

6. **绝不直接写会话日志。** 会话日志是后端内部格式（多帧 zstd、世代命名、lease），
   绕过去只会写坏它。会话里的一切都走 `session.append()`。

7. **前端 `sidebar.right.pane.tab` 是 `kind: "keyed"` 的。** 注册只是"提供一种标签页
   类型"，不会自己出现在界面上，还得被 dispatch 进某个 pane。要"注册即显示"，
   用 `kind: "list"` 的槽。`conversation.input.dock` 正是其一。

## 12. 不做的事

| 不做 | 原因 |
|---|---|
| 资料 / 文件快照 / 记忆 | 上下文里值得留下的只有结果，其余靠模型自己重读 |
| 文件回退 / 撤销 | 改需求用「丢弃 + 追加」 |
| 消息树 UI / 分支切换 | 那是给人看的，核心机制不依赖它 |
| 多目标并行（多个根） | 单活动计划，数据结构已预留扩展 |
| 把计划内容注入提示词 | 提示词必须逐字节不变，否则整个上下文失去缓存 |

## 13. 验收

自检脚本不 import 任何 `@deepseek-ai/*` 运行时包，因此可以在插件目录直接跑。

| 脚本 | 覆盖 |
|---|---|
| `verify-entry.mjs` | 启用/未启用两条装配路径各注册了什么；工具数、提示词段数、闸门挂载 |
| `verify-tools.mjs` | 六个工具的 schema；`result` 必填；检查点闸门放行与拒绝；三级约束 |
| `verify-region.mjs` | 游标推进；同级汇总不被卷走；游标失效时降级追加；检查点提示随汇总落下 |
| `verify-plan.mjs` | 状态流转；连续结束合进一条汇总；自动完成与丢弃级联；渲染不抛错 |

`verify-region.mjs` 用假 session **忠实复刻**了上面 §11.1 的第 2～5 条，
否则测出来的东西不算数。
