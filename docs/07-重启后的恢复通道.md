# 重启 dsh web 后的恢复通道

被暂停（`/task-tree pause` 或条目上的暂停）或被界面停止过的会话，在 dsh web 重启之后
无法恢复继续执行。这份文档记清根因、DSH 侧可用的通道，以及定下来的修复方案。

## 1. 现象

重启 `dsh web` 之后，原本停住的会话：

- 条目上的阶段标签从「已暂停」回到「进行中」，按钮从「继续」变回「暂停」——**点不到继续**；
- `/task-tree resume` 回车之后什么都不发生；
- 会话一直停在 `idle`，只有真人再发一条消息才会继续跑。

## 2. 根因

插件的「被按住」状态有四份，**全在进程内存里**：

| 状态 | 位置 | 谁写入 | 谁清除 | 重启后 |
|---|---|---|---|---|
| `paused` | `pause.js` 的 `Set<sessionId>` | `pause()`、`/task-tree pause`、条目暂停按钮 | `resume()`、真人发言 | 空 |
| `waiters` | `pause.js` 的 `Map<sessionId, Set<release>>` | `waitForResume()` 挂起时 | `release()`、本轮 abort | 空 |
| `stopped` | `auto-continue.js` 的 `Set<sessionId>` | `agent/turn-stopping` 且 `signal.aborted` | 真人发言、`resume()` | 空 |
| `rounds` | `auto-continue.js` 的 `Map<sessionId, number>` | 每次自动续行 | 真人发言归零 | 空 |

暂停闸门挂的是 `agent/pre-step`：挂起时 `waitForResume()` 返回一个**未兑现的 Promise**，
整套 agent 循环就停在那一步。进程一重启，这个 Promise 连同 agent 循环一起没了——
**没有 waiter 可唤醒，也没有标记可清。**

界面侧 `client.js:700` 是 `held = data.paused || data.stopped`，`held` 为真才把按钮画成
「继续」。两份状态一空，用户连继续的入口都看不到；`/task-tree resume` 就算敲了，
`pause.resume()` 也只是 `paused.delete()` 加一个空的 `waiters` 遍历。

一句话：**常规的暂停/继续是"挂住再放行"，而重启把"挂住"这件事本身抹掉了，
放行自然无从谈起。**

## 3. DSH 侧有什么可用

| 通道 | 事实 | 出处 |
|---|---|---|
| `ctx.agents` | 服务，有 `get(id)` / `list()` / `roots()`，**键就是 `sessionId`** | `dsh-agent/README.zh.md`、`lib/index.js` |
| `agent.followup(message)` | 排队一条"下一个轮次"的提示词**并唤醒驱动器** | `dsh-agent/lib/index.js` |
| agent 只在「实时」时存在 | 重启后要由 DSH 自己把它 resume 回来：`dsh-api-session-controller` 的 `resolveAgent(sessionId)`「resolve or resume one ordinary Session」，被 typert 的 agent/session lookup 与所有按 `sessionId` 的 API 请求共用 | `lib/api/session-controller.js`、`lib/types/agent.js` |
| 内置范例 | `dsh-goal-round-driver` 正是在 `agent/status === "idle"` 时用 `followup()` 把会话拉起来 | `dsh-goal-round-driver/lib/index.js` |
| 反例 | 同 profile 的 `dsh-pause` 也是纯进程内存（`Map<sessionId, {enabled, paused, waiting}>`），`release()` 在没有等待中的门时直接返回 false——同样过不了重启，**不能参考** | `profiles/web/node_modules/dsh-pause/lib/index.js` |

关键含义：**插件不能凭空唤醒一个没加载的会话**，但只要会话已被 DSH 恢复成实时
（Web 界面打开这个会话就会触发），`ctx.agents.get(sessionId)` 就能拿到句柄，
`agent.followup()` 就能把它从 `idle` 拉起来。这条路会**往会话里排一条消息**，
与常规暂停/继续的「零痕迹」不同。

## 4. 方案（已与用户确认）

### 4.1 状态持久化

「被按住」改由磁盘承载，**按 `sessionId` 分文件**：`held/<sessionId>.json`

```json
{ "sessionId": "…", "paused": false, "stopped": true, "at": 1759161234567 }
```

- `paused` —— 插件闸门按住（重启后不再"回到未按住"）；
- `stopped` —— 界面按过停止（人主动中断的那次），两者合起来就是界面上的「被按住」。
- 写入沿用「临时文件 + rename」；读不到或坏文件按"没被按住"处理。

### 4.2 界面

`/dsh-tree-task-flow/tree` 的 `paused` / `stopped` 改从持久化状态取，
于是**重启后条目仍显示「已暂停」与「继续」按钮**，用户有入口。

### 4.3 点继续时的分支

`resume(sessionId)` 按顺序：

1. 清掉持久化的 `held` 与内存标记；
2. **有 waiter**（本进程内真挂着）→ `release()` 放行。这是常规路径，**零新增消息**；
3. **没有 waiter**（重启过）→ `ctx.agents.get(sessionId)`：
   - 拿到、且 `agent.status === "idle"`、且本会话计划仍在进行中（`activePath(plan)` 的
     `step` 非空）→ `agent.followup(<续行消息>)`。**这一次恢复会留下一条消息**，
     文本复用 `renderContinue(plan)`，`source` 标 `{ kind: "plugin", plugin: "dsh-tree-task-flow",
     form: "notice", summary: "恢复续行" }`；
   - 拿到但不在 `idle`（正在跑）→ 什么都不做；
   - 拿不到 → 不动手，返回提示：这个会话还没被加载，先打开它，或在其中发一条消息。

### 4.4 其余语义不变

- 真人在暂停期间发言仍然自动解除暂停（`fromHuman` 分支），并顺手清 `held`；
- 暂停仍然是进程内闸门 + 持久化标记，**常规暂停/继续仍然不插任何消息**；
- 暂停态按会话隔离，互不影响。

## 5. 实现要点（文件级）

| 文件 | 改动 |
|---|---|
| `lib/store.js` | 新增 `readHeld(sessionId)` / `writeHeld(sessionId, value)`，落在 `held/` 下 |
| `lib/pause.js` | `paused` 与 `held` 同步读写；`resume()` 增加"无 waiter 时的唤醒分支"；需要一个取 agent 的手段（`ctx.get("agents")`，反射式，不写进 `inject`）与 `activePath` 判断 |
| `lib/auto-continue.js` | `stopped` 同步落 `held`；真人发言时一并清除 |
| `lib/http.js` | `paused` / `stopped` 改读持久化状态 |
| `lib/commands.js` | `resume` 的返回文案要讲清"重启后的这次恢复会往会话里排一条续行消息" |
| `lib/index.js` | 把 `store` 传给 `registerPause`（现在只传了 `autoContinue`） |

已知的坑：

- `ctx.agents` 在某些部署里可能不存在：一律用 `ctx.get()`，取不到就退回"提示用户发消息"；
- `followup` 只能在 `idle` 时用，正在跑的会话不要去推；
- 计划已经结束的会话不该被续行唤醒（`activePath` 为 null 就只清状态）；
- `held` 与 `plans/`、`surfaces/` 一样**只碰插件自己的状态目录**，不写会话日志。

## 6. 验收与自检

`verify-pause.mjs`（扩充）：

1. `pause()` 之后 `held` 落盘，`isPaused` 为真；
2. 模拟重启（新建 registry、空内存、保留 `held` 文件）后：`isPaused` 仍为真；
3. 重启后 `resume()`：无 waiter、拿到假的 idle agent → 调用了 `followup` 且只调一次；
4. 拿不到 agent → 不抛错，返回提示，状态已清；
5. agent 非 idle → 不调 `followup`；
6. 计划已结束 → 不调 `followup`；
7. 真人发言 → 自动解除并清 `held`；
8. 会话之间互不干扰（A 的 held 不影响 B）。

实机（跨进程）：会话暂停 → 杀掉进程 → 重启 → 点继续 → 会话真的接着跑，
并核对会话里只多了那一条续行消息。

## 7. 重启后的端到端验证清单

**前提**：`lib/` 的改动只在 `dsh web` **重启之后**才生效（`link:` 装法，进程启动时加载）。
实测确认：改动前起的那个 GUI 进程里，`resume` 的响应没有 `message`/`woke` 字段，
状态目录下也还没有 `held/`——所以下面这套必须跑在**重启过的**进程上。

| # | 操作 | 预期 | 不对时看哪里 |
|---|---|---|---|
| 1 | 给一个正在跑的会话点「暂停」（或 `/task-tree pause`） | 条目变「已暂停」、按钮变「继续」；`$DSH_HOME/dsh-task-tree/held/<sessionId>.json` 出现且 `paused` 为 `true` | 文件没出现 → 进程还是旧代码，没重启 |
| 2 | 重启 `dsh web` | —— | —— |
| 3 | 重新打开那个会话 | 条目**仍是**「已暂停」、按钮**仍是**「继续」（内存没了，磁盘还在） | 变回「进行中」→ `held` 没读上 |
| 4 | 点「继续」 | 会话从停住的地方接着跑；上下文里多一条「恢复续行」的插件消息 | 见下 |

点继续之后没动静时，看接口返回的那句话（`/dsh-tree-task-flow/action` 的 `message` 字段）：

| `reason` | 含义 | 怎么办 |
|---|---|---|
| `released` | 本进程里真挂着，已放行（零新增消息） | 正常，这是没重启时的路径 |
| `woke` | 已用 `followup` 把 idle 会话推起来 | 正常，这就是跨重启的恢复 |
| `unloaded` | 会话还没被 DSH 加载成实时 agent | 先在界面上打开这个会话，再点一次继续 |
| `busy` | 会话正在跑，不需要唤醒 | 正常 |
| `finished` | 整棵树都已经结束 | 正常，没什么可推进的 |
| `error` | `followup` 抛错 | 看日志里的 warn |

其中 **`unloaded` / `busy` / `error` 三种会保留「被按住」的状态**，你可以再点一次；
只有 `released` / `woke` / `finished` 才会把状态清掉。状态不会因为"试过一次没成"就消失。

## 8. 实机复盘：一次「点了没反应」

2026-09-29 晚用户报「重启后点了没反应，held 目录也没有文件」，逐步查下来是**两个缺陷叠在一起**。

### 8.1 现场

- 服务端 32 个会话全扫一遍、`held/` 目录当时为空 → 界面上那句「已暂停」在那一刻没有服务端依据；
- 但按会话逐一回查，`session-997b83ea` 的 `held/session-997b83ea….json` 确实写出了
  `paused: true`（22:53:14）——**暂停这一半是好的**；
- 旁路实测：对另一个未加载的会话调 `pause` → 文件立刻出现；调 `resume` → 文件消失、返回
  `unloaded`。**写盘与清理也都是好的**。

### 8.2 两个真缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `wakeIdle` 要求 `activePath(plan).step !== null` 才唤醒 | 那个会话最新的目标 `g-mumrxocl1y` 是 pending、任务也是 pending，但**还没拆子任务**（`step === null`）→ 被判成"计划已收尾"，于是不唤醒 |
| 2 | `resume` **先清** `paused` 与 `held`、**再去**唤醒 | 唤醒失败时状态已经没了 → 用户既没有「继续」可再点，也看不到原因，只剩一个停在原地的会话（`held` 看起来"没有文件"） |

外加：界面里 `setError` 之后**没有任何地方渲染它**，失败提示从来就看不见。

### 8.3 改法

- **唤醒判据**：只要 `activePath(plan)` 非 null 就唤醒。`step === null` 有两种含义——
  「任务还没拆子任务」（要模型去 `tree_task_plan`）与「检查点」（要模型拍板这一层完成没有），
  两者都不是收尾；`task === null` 是目标级检查点，同样要唤醒。只有整棵树都结束才不唤醒。
- **状态清理**：`resume` 改成"只有真恢复才清"——`released`（放行挂着的 waiter）、
  `woke`（`followup` 真的推成功）、`finished`（整棵树确实收尾）才清；`unloaded` / `busy` /
  `error` 一律**保留**，用户还能再点一次。
- **界面**：条目上新增一行提示，把这次操作的结果（接口的 `message`）显示出来，8 秒后自动收掉。
- **自检**：`verify-pause` 从 53 项扩到 63 项——新增「任务还没拆子任务时要唤醒」「检查点要唤醒」
  「`followup` 抛错时保留状态」，并把 `unloaded` 场景的期望由"状态清掉"改为"状态保留"。

### 8.4 教训

- **"失败时也把状态清掉"是最坏的一种实现**：用户失去重试入口，也失去原因。只要操作依赖外部
  条件（会话是否已加载、是否 idle），失败就必须保留可重试的状态。
- **判据不要"宁严勿宽"**：`step === null` 看着像收尾，实际是两种"还要干活"的情形。

## 9. 重启后的实机复核（2026-09-29 23:02）

用户重启后（`dsh web` = PID 3804，23:02:16 启动），对修好后的版本做了一次完整复核。

| # | 判据 | 实测 |
|---|---|---|
| 1 | 重启后会话仍被按住 | ✅ `GET /tree` 对 `session-997b83ea` 返回 `paused: true`；`held/session-997b83ea….json` 是重启前（22:53:14）写下的，进程换了它还在 |
| 2 | 点继续能唤醒 | ✅ `POST /action {action:"resume"}` 返回 `{"woke":true,"message":"已把会话从停住的地方推起来…"}` |
| 3 | 恢复后状态被清 | ✅ `held/` 目录随即变空，`paused` / `stopped` 均为 `false` |
| 4 | 会话真的接着跑 | ✅ 表层重建显示 `#4074 user/message [plugin:dsh-tree-task-flow] 接下来需要进行任务：「任务 1：用重采样替掉丢帧」(t-mumroxocl1z)。`——这条就是 `agent.followup()` 排进去的恢复续行消息；紧随其后的 `#4076` 起模型开始 `edit` |

这次复核正好撞在修复前的误判场景上：那个会话的计划是「目标 `g-mumrxocl1y` pending、任务
`t-mumroxocl1z` pending、**还没拆子任务**」（`step === null`），旧判据会判成 `finished` 而不唤醒，
新判据正确唤醒并给了它"接下来需要进行任务…"这句话。

两条说明：

- 复核走的是插件 HTTP 接口（`/dsh-tree-task-flow/action`），**与条目上那个圆形按钮是同一条路径**；
  按钮本身的点击链路没有单独验证。
- 随后 `#4078` 起那个会话出现 `Error: cannot modify …PlaybackGroup.cs`，是**那个项目自己的编辑失败**，
  与本插件无关——本插件的职责到"把它推起来"为止。

## 10. 「点继续时其他会话也继续了」的排查

用户反馈：给 AudioStream 那个会话点继续之后，几只"之前手动暂停过"的会话也在跑。现场证据：

| 证据 | 结果 |
|---|---|
| `held/` 目录 | 只有 `session-997b83ea.json` 一个文件（`paused: true`），**没有第二个** |
| 32 个有条目的会话逐个查 `/tree` | 除它以外 `paused` / `stopped` 全是 `false` |
| 最近有日志写入的三只会话（`6aa36fa5` / `fa6ebffe` / `7e56a35b`） | 既没有 `plans/` 也没有 `held/`——**它们没有树形任务流条目**，不可能被本插件按住或放行 |

为什么不是"继续"株连的：

- `resume(sessionId)` 只碰一个会话：`paused.delete(sessionId)`、`patchHeld(sessionId, …)`、
  `autoContinue.resume(sessionId)`，没有循环、没有"广播"；
- `held` 是**按会话一文件**，清理只删自己那一个（`verify-pause` 里有"会话之间互不干扰"场景）；
- 插件里不存在任何批量唤醒的代码路径。

真正的原因：**那些暂停点发生在 23:02:16 重启之前的旧进程里**，旧代码只在内存 `Set` 里记，
从来不落盘。重启之后它们本来就"不再被按住"——不是被这次"继续"放出来的，而是**重启那一刻就已经
松开了**。这正是本次要修的问题，但修复只对**重启之后新点的暂停**生效；修复前点的暂停无从追溯。

自查路径（新代码下）：

1. 给任一会话点「暂停」→ `~\.dsh\dsh-task-tree\held\` 下应出现 `<该会话 sessionId>.json`，
   其他会话的文件不受影响；
2. 点「继续」→ 只有该会话那一份消失；
3. 重启 `dsh web` → 该会话条目仍显示「已暂停」。

另外一件事值得知道：DSH **内置**的目标轮次驱动（`dsh-goal-round-driver`）在会话 `idle` 且持有
活跃 goal 时，会自己 `followup` 把会话推进下去。如果"自己跑起来"的那些会话用的是内置
`goal_*` 工具，那是它的行为，与本插件无关；本插件按设计**绝不挂到它上面**。
